# Lightning-RAG  软件设计文档

## 1. 目标与范围

本设计描述 Lightning-RAG的整体结构、关键数据流与实现约束。

- 保留三态内核、五级上下文压缩、工具协议、记忆/技能/MCP 设计；
- PDF 解析采用 **Ovis** 与 **PDFKit + Vision** 两条路径；
- 向量库用 **SQLite + sqlite-vec + FTS5** 取代 LanceDB；
- GUI界面用 **SwiftUI** ；
- 用 **swift-transformers**、**mlx-swift-lm**、**onnxruntime-swift** 实现切片、分词与本地模型。

## 2. 分层结构

```
┌────────────────────────────────────────────────────────────┐
│ BaseAgentApp（SwiftUI）                                     │
│ 主窗口：对话 / 任务计划 / 思考；独立：配置 / 日志             │
└───────────────────────────┬────────────────────────────────┘
                            │ AgentCallbacks
┌───────────────────────────▼────────────────────────────────┐
│ Agent（门面）                                               │
│ run / 自动续跑 / 系统提示 / 事实抽取 / L4 蒸馏               │
├────────────────────────────────────────────────────────────┤
│ KernelLoop（控制流）  Session/Budget/Compressor（上下文）    │
│   THINK → ACT → CONSOLIDATE                                │
├────────────────────────────────────────────────────────────┤
│ 能力层                                                      │
│  ToolRegistry / AgentTool / 并行分发 / 确认策略              │
│  Tools: 文件/代码/Shell/Web/Memory/Skill/RAG/MCP/Plan       │
├────────────────────────────────────────────────────────────┤
│ 知识与模型层                                                 │
│  RAGEngine → Parsers → TextChunker → Embedding → VectorStore│
│  LocalModelFactory → MLX / ONNX / Tokenizers                │
└────────────────────────────────────────────────────────────┘
```

依赖方向单向向下：UI 只依赖 `AgentCallbacks`；Agent 依赖内核与工具；内核只依赖注入闭包与 `AgentTool` 协议；RAG 与模型层不感知 Agent。

## 3. 运行时循环

### 3.1 一次用户轮次

1. `Agent.run(userInput)` 记录请求、恢复工作检查点、处理计划边界、推送计划到 UI。
2. `KernelLoop.run` 进入 `THINK`：
   - `Session.buildMessages` 生成系统提示 + 折叠摘要 + 原文窗口 + 锚点；
   - `ContextBudget` 按 system / tools / earlier / raw / reserve 分区记账；
   - 调用 `LLMService.chatStream`，流式转发 content / reasoning。
3. 若模型返回 tool_calls → `ACT`：
   - `AgentToolDispatcher` 解析参数、检查取消、确认策略；
   - 只读工具（`web_scan`、`rag_search`、`rag_outline`、`skill_search`、`skill_semantic_search`、`memory_search`）按批并发，最多 8；
   - 每个 tool_call 都必须回填 ToolResult，避免悬挂调用导致 API 400。
4. 工具结果按 L0/L1 处理后回注，进入下一轮 `THINK`。
5. 达到收敛条件 → `CONSOLIDATE`（每 8 轮，配置值下限 8）或直接结束。
6. `Agent` 处理自动续跑：`max_turns` 或「DONE 但计划未完成」时，最多续 4 段，并在段间传递失败快照（含重复调用、步骤内失败计数等）；`start_long_term_update` 触发的蒸馏标记在门面层跨段累计，不会因分段重置丢失。
7. 整个用户轮次结束后触发一次 `hooks.finished`：事实抽取与 L4 蒸馏各一次。
8. 空回复按 `ExitReason` 分别提示：取消、LLM 错误、模型无可见正文、轮次上限不再共用同一条误导文案；重复调用达到上限时保留模型最后一轮正文。

### 3.2 五级压缩

| 级别 | 触发 | 行为 |
| --- | --- | --- |
| L0 | 工具返回 | 捕获并硬截断 20k 字符 |
| L1 | 注入上下文前 | 按剩余预算 head+tail 裁剪；HTML 标签白名单去噪，保留源码尖括号 |
| L2 | 轮次转摘要 | `<summary>` 首句 / 工具名摘要 |
| L3 | 原文窗口超预算 / 每 8 轮 | 折叠到 `raw_turns + 1` 轮；`rawTurns` 至少覆盖一个 consolidate 周期，避免窗口每回合滑动改写消息前缀；连续相同摘要按去掉 `[T{n}]` 前缀后的正文合并 |
| L4 | `start_long_term_update` / 长任务 | LLM 蒸馏 facts / lessons / skill |

`ContextBudget` 与 `Session` 共用同一个预算对象，避免「内核记账」与「Session 折叠」两本账。

## 4. 工具与能力层

### 4.1 协议

```swift
protocol AgentTool {
    var name: String
    var description: String
    var parameters: JSONValue   // JSON Schema
    var destructive: Bool
    func shouldConfirm(_ args: [String: JSONValue]) -> Bool
    func run(_ args: [String: JSONValue]) async throws -> ToolResult
}
```

`ToolRegistry` 负责注册、查找、schema 缓存与工具关闭。工具不直接持有 UI，只通过 `AgentCallbacks` 与 `ToolRegistry.session` 访问共享状态。

### 4.2 工作区安全

- 所有文件路径先 `resolvingSymlinksInPath` 再 `standardizedFileURL`，校验 workspace 前缀；
- `file_write` 有单次写入字符上限，超限要求分片或 `shell_run`；
- `file_modify` 默认替换第一处，`replace_all=true` 才批量替换（与参考实现一致）；
- Python `code_run` 通过 `sitecustomize` 拦截 `builtins.open` / `io.open` / `os.open` 的写模式，工作区外写入抛 `PermissionError`，同时放行 subprocess 的 int fd 管道；
- `code_run` / `shell_run` 运行在受控 `Process` 中，带超时、输出上限；超时/取消递归终止进程树（先子后父），避免 shell/npx 孤儿；
- `web_scan` 首请求与每次重定向都先解析目标，阻断 loopback/私网/link-local/云元数据（SSRF）；响应上限 8MB、重定向 5 次，任务取消时通过 `withTaskCancellationHandler` 立即取消 dataTask 并 resume，避免 continuation 悬空；
- 确认策略由 `RiskPolicy` 统一判定，`always_confirm_code` 强制确认；路径扫描覆盖裸 `~`、`/`、`..`、`$HOME`/`${HOME}`，并用 lookbehind 避免把 `./` 误判为根目录；UI 确认弹窗默认按钮为「拒绝」；
- `shell_run` / `code_run` 失败时把截断后的 stdout/stderr 并入 error，模型不会只看到 `Exit code 1`；
- `AtomicFile` 使用同目录临时文件 + 原子替换；Manifest 使用 `.lock` 文件 `flock` 跨进程串行；
- MCP 子进程异常退出后 `callTool` 自动重连一次；`start()` 串行化，`shutdown()` 后禁止复活，接收缓冲上限 8MB，`notifications/tools/list_changed` 会重新注册工具并失效 schema 缓存。

### 4.3 计划与工作记忆

- `update_plan` 同时写 `<workspace>/.agent/plan.json` 与 `Session.working["plan"]`，保证本轮反思门可见、跨会话可恢复；
- `update_working_checkpoint` 立即写 `Session.key_info`（本轮可见），`persist=true` 时才额外落盘供跨会话恢复；
- 任务边界处理：旧计划全部终态 → 清空；仍有 open 步骤 → 注入「新任务 or 继续」判断提示。

## 5. RAG

### 5.1 同步流程

```
扫描知识库（扩展名白名单，跳过 .rag）
  → Manifest 比对（mtime + size + 源文件指纹）
  → [最多 6 个文件并发] 解析（ovis / vision / epub / office / html / text）
  → DocumentCleaner
  → TextChunker（结构 → 语义 → 递归）
  → Embedding（共享调度器串行，子批 2...32 自适应，上限可配；nomic / jina-v3 先做 Matryoshka 截断并重新归一化）
  → VectorStore.add（单事务：正文 + FTS + 向量）
  → 写 Markdown 缓存与 documents 摘要
  → Manifest 合并落盘
```

多文件处理使用 worker 池（`rag_ingest_concurrency`，默认 6）：每个文件独立解析器实例，解析/OCR 与其它文件的切片/embedding/入库重叠进行。embedding 仍是单模型串行，由 `AdaptiveEmbeddingScheduler` 统一排队；子批从 `rag_embedding_initial_batch`（默认 16）开始，按吞吐每 `rag_embedding_probe_batches` 批（默认 2）或 `rag_embedding_probe_seconds` 秒（默认 2）探测一次，提速且进程内存低于 `rag_embedding_memory_limit_mb`（默认 6144）时按 `rag_embedding_batch_step`（默认 2）上探，吞吐下降或内存超限时下探，范围由 `rag_embedding_min_batch`（默认 2）到 `rag_embedding_max_batch`（默认 32，2...256）。吞吐变化小于 `rag_embedding_throughput_tolerance`（默认 0.03 = ±3%）时视为测量噪声、不调整；实测 bge 477 token 长块在 batch 4-16 已到吞吐平台，同 batch 重复测量噪声可达 ±20%，可把容差调到 0.08-0.10。设置窗口高级区用单独一行展示全部 8 项（下限、上限、步进、启动预设、探测批次、探测窗口、内存阈值、吞吐容差），保存时按 `Config.migrate()` 的同一顺序收口。

DocumentCleaner 先暂存围栏代码块与行内代码（占位符使用私用区字符，避免被控制字符归一化破坏），再处理 HTML `<table>`：简单表格转 GFM（兼容缺失闭合标签、`<br>`），含 `colspan`/`rowspan`、嵌套表格、`caption`、多行表头或单元格内列表/图片/公式等复杂表格保留原始 HTML `<table>`（用占位符避开后续标签清理），最后清理 HTML/实体/URL/噪声行。实体按含义解码（`&amp;` → `&`、`&hellip;` → `…`）；块级标签保留段落换行，内联标签直接删除；script/style/SVG/iframe 等容器整块移除，属性与 CSS 残片单独清理。自动识别 Markdown 时保留标题、列表、引用、链接、表格、分隔线、代码与缩进；纯文本则把链接压成文字并去掉 URL/邮箱。Unicode 层删除 NBSP、零宽/方向控制符、软连字符、BOM、U+FFFD、变体选择符、私用区、非字符与孤立组合符；合并汉字间的 OCR 空格；把连续点号归一为 `……` 并压缩重复中文标点；按「有效字符/符号密度/装饰符号数量」过滤 OCR 噪声行，连续重复行去重。中文硬换行在两侧均为 CJK 时不补空格；纯数字行只在页首/页尾 3 个非空行内视为页码，正文中的年份/编号不会被误删。最后统一做密度压缩：去掉行尾空格，页标记、连续列表项、表格行、引用行之间不保留空行；短 OCR 行合并，长段落之间保留一个空行；标题、代码块与保留的 HTML 表格前后保留结构分隔。压缩在还原代码/HTML 表格之前完成，代码与表格内部空行不受影响。

清洗分两档（`DocumentProfile`）：**`.structured`** 用于结构化文档（HTML / Office / EPUB / CSV / JSON / MD / 代码等，按扩展名自动判定），不做 URL/邮箱删除、散落数据行删除、短行删除与硬换行合并，并保留原有段落空行——原文档的换行本身就是段落边界（`w:br`、`<br>`、表格行），合并会破坏结构；**`.ocr`** 用于 PDF 与图片，保留全部 OCR 噪声处理（汉字间空格、噪声行、URL/邮箱、页码等）。档位写入 `metadata["clean_profile"]` 便于诊断。清洗规则变化时递增 ingest 签名的 `pipeline_version`，旧文件会在下次同步时重建。

PDF 页面渲染使用 `CGPDFPage.getDrawingTransform`（而不是手工翻转 CGContext），保证 CropBox、`/Rotate` 与坐标原点正确；否则扫描页会被整体旋转 180°，Vision OCR 输出大量乱码。渲染/清洗逻辑变化通过 ingest 签名的 `pipeline_version` 触发旧缓存重建。

manifest 每条记录包含 `ingestSignature`、`chunkCount`、`complete`。增量跳过前会校验库内该来源的实际切片数与 Markdown 缓存；缺失切片、旧版无完成标记、失败页计数大于 0 都会强制重建。失败页不阻断已成功内容的入库，但 `complete=false` 会让下次同步继续重试；用户取消或进程退出时不写完成条目。

重复文件处理分两层：同步前用「文件大小 + 采样指纹」分组，同一本书的不同目录副本只保留一个代表文件参与解析。分组时先按大小归类，只有大小相同的文件才计算采样指纹，避免对绝大多数唯一大小文件做无谓的磁盘读取。解析完成后按清洗正文的 `content_hash` 全局去重，保留一个来源并删除其余来源的 chunks/documents/Markdown 缓存。被去重的正文副本写入 `duplicateOf` tombstone，下次增量同步直接跳过，不再重复解析；tombstone 不参与 content_hash 分组。知识库根目录用 `realpath` 规范化，避免 `/var`、`/private/var` 等 firmlink 造成相对路径与 manifest 键不一致。

手动「向量去重」入口位于知识同步配置区：点击后分页扫描 `chunks`，按切片正文 SHA256 前 128 bit 分组，`ORDER BY created_at ASC, rowid ASC` 每组只保留入库时间最早的一份，并在单事务内按 rowid 删除其余切片/全文索引/向量。仍有剩余切片的来源刷新 manifest 的 `chunkCount`；整个来源被清空时同步删除 documents 与 Markdown 缓存，并写 `duplicateOf` tombstone（`chunkCount=0`、`complete=false`、清空 `digest`），下次增量同步直接跳过副本。去重与同步、模型加载/卸载、对话发送互斥，完成后刷新底部 RAG 统计。

删除文件：同一事务按 rowid 分批删除 `chunks` / `chunks_fts` / `chunk_vectors`，同时删除 `documents` 摘要记录并清理 Markdown 缓存。

Manifest 使用原子读改写 + 独立 `.lock` 文件的 `flock`，跨进程串行化且只覆盖本次触达条目，避免并发同步互相覆盖。

同步一致性处理：

- ingest 签名覆盖 PDF 引擎、扫描版 EPUB OCR 引擎、OCR 模型/路径、预处理/二值化开关、切片参数（大小 / overlap / 语义切片开关）、embedding 后端 / 权重目录 / 模型名、向量元素类型与 Matryoshka 截断维；签名按文件记录在 manifest 条目中，签名变化时只逐文件重建，已完成的文件保留；
- 每个文件 `store.add` 成功后立即合并落盘 manifest，用户中途停止或进程退出后，下次同步只处理签名不一致、指纹变化或缺失条目的文件；
- 显式 `force=true` 会先把所有条目标记为待重建，取消后未处理文件仍保持待重建状态，可从断点续跑；
- 维度 / 元素类型 / 索引指纹（embedding 模型、Matryoshka 维）变化时**不清空旧数据**：只标记 `rebuildReason`，向量通道关闭、`ingest` 拒绝写入、全文检索仍可用；用户执行「重建向量库」后才清空 chunks/documents/ANN 与 manifest 并按当前配置全量同步。空库则直接采纳新配置（无数据损失）；向量库被删除但 manifest 残留时仍会自动全量重建；
- 单个文件变更后解析失败：删除其旧切片、documents 与 Markdown 缓存，并立即移除 manifest 条目，下次同步会重试而不是跳过；
- `cancel()` 在文件边界、embedding 子批边界以及解析完成后都会检查；PDF/EPUB 的逐页与 Vision/Ovis OCR 循环也会在页边界检查 `Task.isCancelled`，取消不会被误记为失败页。取消不算解析失败，不会清掉已有索引，已完成文件会保留，其他 worker 会在下一个检查点退出；
- `close()` 遇到在途同步会记录 `closePending` 并立即取消同步，等 ingest 收尾后自动关闭连接；延迟关闭会重新抢占 ingest 标志，若已有新同步开始则保留 pending 交给它收尾，绝不会把 `cancelRequested` 写到新同步上。`reload()` 仍跳过以免打断事务。

### 5.2 存储 Schema

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);

CREATE TABLE chunks (
  rowid INTEGER PRIMARY KEY AUTOINCREMENT,
  id TEXT NOT NULL UNIQUE,
  source TEXT NOT NULL,
  source_hash TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,
  text TEXT NOT NULL,
  heading TEXT NOT NULL DEFAULT '',
  metadata TEXT NOT NULL DEFAULT '{}',
  created_at REAL NOT NULL
);
CREATE INDEX idx_chunks_source_hash ON chunks(source_hash, chunk_index);

CREATE VIRTUAL TABLE chunks_fts USING fts5(
  tokens,
  source_hash UNINDEXED,
  chunk_index UNINDEXED,
  tokenize = 'unicode61 remove_diacritics 2'
);

-- 向量表按 rag_vector_element_type 建表（N = embedding 生效维度，默认 int8）
CREATE VIRTUAL TABLE chunk_vectors USING vec0(
  embedding int8[N] distance_metric=cosine     -- int8（默认）
);
-- fp32: embedding float[N] distance_metric=cosine
-- bin : embedding bit[N]                       -- 固定汉明距离，不接受 distance_metric
-- fp16: sqlite-vec 0.1.9 没有该元素类型，打开向量库时直接报错并提示改类型

CREATE TABLE documents (
  doc_id TEXT PRIMARY KEY,
  doc_name TEXT NOT NULL,
  digest TEXT NOT NULL DEFAULT '',
  chapters TEXT NOT NULL DEFAULT '',
  md_path TEXT NOT NULL DEFAULT '',
  updated_at REAL NOT NULL
);

-- ANN 索引（分块 IVF，按需构建；详见 5.4.1）
CREATE TABLE ann_blocks (
  block_id INTEGER PRIMARY KEY,
  clusters INTEGER NOT NULL,
  dim INTEGER NOT NULL,
  payload BLOB NOT NULL          -- int8 量化簇心：clusters × dim 个 int8 + 每簇 scale
);
CREATE TABLE ann_cells (
  block_id INTEGER NOT NULL,
  cluster_id INTEGER NOT NULL,
  seq INTEGER NOT NULL,
  count INTEGER NOT NULL,
  payload BLOB NOT NULL,         -- dense：[rowid i64][scale f32][int8 × dim] × count
                                 -- bits ：[rowid i64][dim/8 字节位图] × count
  PRIMARY KEY (block_id, cluster_id, seq)
) WITHOUT ROWID;
```

说明：

- FTS 存 **预分词后的 tokens**，不是原文；原文只在 `chunks.text` 保存一份。
- CJK 经 `NLTokenizer` 词级切分后追加 bigram，解决 unicode61 对中文整段成词的问题。
- `chunk_vectors` 的 rowid 与 `chunks.rowid` 一一对应；向量表不存正文。
- 单行字节数：fp32 `4 × N`、int8 `N`、bin `ceil(N / 8)`。512 维时 int8 每行 512B，是 fp32 的 1/4、bin 的 8 倍。
- 维度记录在 `meta.embedding_dim`，元素类型记录在 `meta.vector_element_type`，二者与 `meta.vector_index_fingerprint`（`embedding.identifier | dimension | matryoshkaDim | elementType`）共同构成索引指纹。
- 指纹不符时**不静默删数据**：非空库只设置 `rebuildReason`，保留旧切片与全文索引，关闭向量通道并拒绝写入，等待用户显式「重建向量库」；空库则直接采纳新配置并丢弃空表与 ANN 索引。待重建时不会把新配置写回 meta，重启后仍会要求重建，避免下次打开误判为已生效而按新类型重建向量表。
- 极少数模型缺少 `config.json`，首轮推理后才发现真实维度；空库会按实际输出维度重建向量表，非空库明确报错，避免静默清空知识库。

### 5.3 写入与删除事务

写入：

```
BEGIN IMMEDIATE
  DELETE chunks/fts/vectors WHERE source_hash = ?（按批）
  for batch in chunks:
      INSERT chunks ... RETURNING rowid
      INSERT chunks_fts(rowid, tokens, source_hash, chunk_index)
      INSERT chunk_vectors(rowid, vec_int8(?))       -- int8；bin 用 vec_bit(?)，fp32 直接 ?
COMMIT
```

写入向量前统一做两步：`VectorCodec.normalize` 保证单位长度，再按 `rag_vector_element_type` 编码（int8 为对称量化 `clamp(round(x × 127), -127, 127)`，bin 为 LSB-first 符号位，fp32 原样）。`int8` / `bit` 必须用 `vec_int8(?)` / `vec_bit(?)` 包一层，否则 sqlite-vec 会把裸 BLOB 一律按 float32 解析。Matryoshka 截断（jina-v3 默认取前 256 维）与重新归一化在 embedding 层完成，写入侧不再截断。

删除：

```
BEGIN IMMEDIATE
  SELECT rowid FROM chunks WHERE source_hash = ?
  for batch of 400:
      DELETE chunks WHERE rowid IN (...)
      DELETE chunks_fts WHERE rowid IN (...)
      DELETE chunk_vectors WHERE rowid IN (...)
COMMIT
```

任何一步失败都会整体 `ROLLBACK`，包括已经执行的旧数据删除。

### 5.4 检索

**向量 KNN（两段式）**

1. `SELECT rowid, distance FROM chunk_vectors WHERE embedding MATCH vec_int8(?) AND k = ?`（bin 用 `vec_bit(?)`，fp32 用裸 `?`）
2. `SELECT rowid, text, source, chunk_index, heading FROM chunks WHERE rowid IN (...)`

查询侧与入库侧执行完全相同的变换：Matryoshka 截断 → 重新归一化 → 按元素类型量化。`int8` / `bin` 的查询向量同样必须包 `vec_int8()` / `vec_bit()`。相似度换算按列类型区分：fp32 / int8 为 `max(0, 1 - distance)`（余弦距离），bin 为 `max(0, 1 - distance / dim)`（汉明距离折算）。

不 JOIN 虚拟表。定向检索（`source` / `source_contains`）时先放大 k（topK×20，首轮即夹到 4096），第二阶段过滤；不足则继续放大。

`search` / `searchFTS` 在 VectorStore 的同一把锁内完成「虚拟表命中 + 主表 hydrate」，写入/删除无法在两段之间提交；RAGEngine 另用 `searchLock` 保护整段读，`close()`/`reload()` 会等读操作结束再关闭连接。

**FTS5**

- 查询词与索引使用同一 `TextAnalyzer.ftsTokens`；
- `bm25()` 越小越相关，归一化为 `raw / (1 + raw)`；
- 定向检索时同样 over-fetch 后在第二阶段过滤。

**RRF 融合**

```
score(rowid) = Σ 1 / (k + rank_i)     # k = 60
```

向量与 FTS 两路各 over-fetch `topK × overfetch × 4`，按 rowid 去重融合。配置可启用 reranker（`rag_rerank_enabled`，默认开启），对候选做交叉编码重排，低于 `rag_rerank_threshold`（默认 0.45，适配 jina ONNX 的分数分布）的结果丢弃；全部低于阈值时回退原排序的候选，避免模型完全拿不到上下文。

**重排序后的条数由 `rag_rerank_top_n` 决定**（默认 5，1...20，设置面板 Reranker 行的「TopN」），分数过滤下限由 `rag_rerank_threshold` 决定（默认 0.45，0...1，设置面板 Reranker 行的「阈值」）：候选池按 `max(调用方 top_k, TopN) × 4` 取，重排并按阈值过滤后只返回分数最高的 TopN 条。关闭重排序时不看 TopN，仍按调用方 `top_k`（`rag_search` 默认 5、范围 1...10）返回 RRF 排序结果。`search` 的最终条数统一封顶 20。

### 5.4.1 ANN 索引（分块 IVF）

sqlite-vec 的 `embedding MATCH` 没有 ANN：它是逐行算距离的全表扫描。真实库实测（59.9GB / 2115 万切片 / dim=512，外置 USB SSD）只有约 10MB/s（20 万行 40.28s，≈4965 行/s），叠加只读超时（5s）后大库检索会长期被跳过，因此 `VectorStoreANN.swift` 在同一个 `index.sqlite` 里维护一套分块 IVF 索引（表结构见 5.2）：

- **分块（block-local IVF）**：块大小 = `rag_ann_clusters` × `rag_ann_cluster_size`（默认 256 × 512 = 131072 行），按 rowid 顺序切块，块内独立 k-means（训练采样上限 8192 行）。峰值内存只与块大小有关（约 200MB），与库规模无关，2115 万切片也能在普通机器上构建。
- **int8 量化**：fp32 库的向量与簇心都按 `scale = max|x| / 127` 量化，每行 `[rowid Int64][scale Float32][int8 × dim]`（dim=512 时 524B/行，2100 万行约 11GB）；int8 库直接复用入库码值（scale=1，不再二次量化），体积与向量表同量级；bin 库保存 `dim/8` 字节位图（512 维 72B/行），打分用汉明距离。簇心始终是 int8 码 + 每簇 scale（bin 向量按 `±1/√dim` 还原后做 k-means）。粗排误差由下面的精确重打分兜底。
- **落盘布局**：`ann_cells` 按 (block_id, cluster_id, seq) 聚簇写入，主键即顺序读游标（`WITHOUT ROWID`），检索时读到的就是命中的簇，而不是散布全表的行；簇心与元数据（`ann_ver` = 2 / `ann_clusters` / `ann_block_rows` / `ann_dim` / `ann_element_type` / `ann_blocks` / `ann_rows` / `ann_last_rowid` / `ann_built_at`）存 `ann_blocks` 与 `meta`，元数据缺失即视为「未构建」。
- **查询**：逐块对簇心打分选 top-`rag_ann_nprobe`（簇心常驻内存缓存，块粒度失效），顺序读命中簇并批量打分：int8 / fp32 用内积（`dot × scale / 127` 或 `dot`），bin 用汉明距离并折算 `1 - hamming/dim`。取候选池（定向检索 topK×20，否则 topK×8）后由 `rag_ann_rescore`（默认 32）条走精确向量（`chunk_vectors` 点查）重打分，最后复用精确路径的 `hydrate`（主表取正文 + 源过滤）。查询向量与簇心都是归一化向量，内积即余弦相似度。
- **尾块补齐**：同步是「按来源先删后插」，旧 rowid 会失效，所以索引以 **rowid 水位** `ann_last_rowid` 为界，而不是「已索引条数」。水位之后的切片（含重新同步产生的新 rowid）由 `scanANNTailLocked` 按 rowid 顺序精确补齐，读取预算 128MB（dim=512 时 int8 约 13 万行、bin 约 186 万行）；状态里的尾块行数用「计数器差」与「水位后的 `COUNT`（封顶 `cap+1` 行）」取大，避免重同步后少算。超过预算时索引标记 `needsRebuild`，`annSearch` 返回 nil 由 `search` 回退精确路径并在界面提示重建。
- **构建**：`buildANNIndex` 逐块训练/量化/写入，每块一个事务，块间检查取消（可中断，已写完的块保留，再次构建从断点续建）；格式版本（`ann_ver`）、维度、元素类型、聚类参数任一变化时整体重建。读取走影子表快通道 `streamStoredVectors`：`_rowids` 流式扫描 + 按 chunk_id 懒读打包 blob（实测 115MB/s），首行布局校验失败则回退官方 `SELECT rowid, embedding`（10MB/s，并检测乱序后排序兜底）。首次构建 2115 万切片预计约 10 分钟。
- **自动维护**：同步结束后若库内切片 ≥ `rag_ann_min_chunks`（默认 20000）且 `rag_ann_auto_build` 打开，未构建时自动建；已构建但尾块超过 `max(min_chunks/2, blockRows/4)` 或存在超出补齐预算的切片时自动续建；小库不建（精确扫描更快）。
- **互斥**：构建与同步/去重/清空共用 ingest 标志串行，`cancel()` 同样能中断构建；构建期间只读查询按 5s 超时跳过（与同步期间行为一致），因此配置面板只在空闲时允许启动，并提供「构建 ANN 索引 / 停止构建 / 删除索引」与状态摘要（`rag_status` 也输出 `ann_index` / `ann_usable` / `ann_needs_rebuild`）。

### 5.4.2 Matryoshka 与向量量化

默认 embedding 是 `models/jina-embeddings-v3-mlx-int4`（MLX 加载，原生 1024 维）。jina-v3 与 nomic 都支持俄罗斯套娃表示：前若干维本身就是一个可用的低维向量。`MatryoshkaEmbedding` 包装 provider，入库与查询共用同一实例，保证两侧变换完全一致：

1. **截断**：取完整向量的前 N 维（`rag_matryoshka_dim` ∈ {128, 256, 512}，默认 256）；
2. **重新归一化**：截断会破坏 L2 范数，必须重新计算范数并归一化，不能复用完整向量的归一化结果；
3. **量化**：int8 采用对称量化 `clamp(round(x × 127), -127, 127)`。禁止使用 sqlite-vec 的 `vec_quantize_int8(..., 'unit')`——它是非对称映射，会破坏余弦相似度；bin 取符号位并按 LSB-first 打包（`out[i/8] |= sign << (i%8)`）；fp32 原样保存。

`rag_matryoshka` 默认 `auto`：provider 标识包含 `nomic` 或 `jina-embeddings-v3` 时启用，截断维严格跟随 `rag_matryoshka_dim`；`on` 对任何模型都截断（可用于其它支持 MRL 的模型），`off` 关闭。目标维不小于原生维度时不包装。包装后的 `identifier` 追加 `#mrlN`，因此切换截断维会改变索引指纹并触发显式重建。

非 Matryoshka embedding 不做截断，但同样在入库与查询两侧执行 FP32 → 目标元素类型的量化。元素类型为 `fp16` 时直接报错（sqlite-vec 0.1.9 不支持），设置面板保存配置时即提示改用 int8 / fp32 / bin，不会创建错误的表。

### 5.5 PDF 三引擎

| 引擎 | 路径 | 适用 |
| --- | --- | --- |
| `ovis`（默认） | 先走 PDFKit 文本层：每页有效字符 ≥ 50 → 直接提取并清洗为 Markdown；文字页检测到表格 → 仅裁剪表格区域（300 DPI）→ 归一化 → OvisOCR2 `tableToMarkdown` → 替换回原位置；不足 50 → PDFKit 渲染（最长边 1408，200 DPI）→ OvisOCR2 整页 Markdown | 混合文本/扫描书籍、带表格的文字版 PDF、复杂版面 |
| `vision` | 先走 PDFKit 文本层（每页有效字符 ≥ 50）→ 否则渲染 + 归一化 + Vision OCR | 无 Ovis 模型时的通用方案 |
| `hybrid` | 文本层同上；扫描页按 8 页一批渲染，批内非表格页并发走 Vision，表格页或 Vision 文本过少的页面回退 OvisOCR2 | 扫描书籍最快，兼顾表格结构 |

Ovis 视觉模型延迟到真正遇到扫描页或文字页表格时才解析/加载，纯文字且无表格的 PDF 不依赖 Ovis；纯 `ovis` 模式的视觉调用串行执行（共享 ModelContainer），单页失败只记录并跳过，不再让整本书失败。`hybrid` 模式下 Vision 在批内并发（每文件 8 页，跨文件总量由全局信号量限制到 CPU 核心数），只有表格页与低置信度页进入串行 Ovis，显著提升扫描书吞吐。文本页与扫描页按原页序合并，统一走 `DocumentCleaner` 清洗。

**文本层内存安全**：PDFKit 的 `PDFPage.string` 在图片密集页会触发病态文本行布局（实测 392 张图的单页可涨到数十 GB）。`PDFTextExtractor` 先读取页面 `/Resources` 的图片 XObject 画像（不解码图片），满足「图片数 ≥16、单图 ≥3200 万像素、页面总像素 ≥6400 万」任一条件时，整页改用有界 `CGPDFScanner`（字体 + ToUnicode + 文本状态）提取；扫描器无文本时直接进入 OCR，绝不回退 PDFKit。普通整页扫描图（400 万～600 万像素）仍走 PDFKit：实测 30 页仅需 0.06s 且内存稳定，改走扫描器会慢 30～50 倍，因此像素阈值只兜底极端大图。所有文件的文本层提取共享全局闸门（默认 CPU 核数、封顶 8 路），页面对象在闸门内的 `autoreleasepool` 中创建与释放。知识库同步同时按体积分批：≥16MB 的文件单独成批、批间串行，轻文件按 `rag_ingest_concurrency`（最多 6）并发解析；单个文件内部再由 `PDFProcessingPlan` 按体积收紧 worker、在途页与批大小。解析/OCR 失败页（含渲染失败）计入 `failed_pages`，该文件标记为未完整完成并在下次增量同步重试。

**水印文本层**：扫描书常把「每页相同的网址水印」写进文本层，原始有效字数可能超过 50 字阈值，但清洗时会被当作跨页页眉页脚整行删除，最终正文为空。Vision/Ovis 两条路径在全部页文本提取完后统一判定：`DocumentCleaner.repeatedMarginKeys` 找出跨页重复页眉/页脚（每页首尾各 3 个非空行、覆盖 ≥50% 页面），再用 `effectiveOCRTextCharacterCount` 排除这些行、同页重复行和 URL/邮箱后的字符数决定是否 OCR，避免「有水印无正文」的扫描书被误判为文字版而跳过 OCR。

文字页表格检测基于 PDFKit 文本行的多列特征（Markdown 管道符、连续多空格/制表符分隔）；检测到连续 ≥2 行（或单行含管道符）时，用 `PDFSelection.bounds(for:)` 取得表格区域，从高 DPI 整页位图中裁剪、归一化后调用 Ovis 的 `tableToMarkdown`，返回的 Markdown 表格替换原文本范围。旋转页暂不裁剪，保留文本层。

Vision 归一化：长边压缩到 1500 → 灰度 → 1%/99% 对比度拉伸 → 3×3 锐化 → 可选 Otsu 二值化。识别结果按归一化坐标聚类，恢复阅读顺序与段落。

### 5.6 EPUB

`ZipFoundation` 解包 → `META-INF/container.xml` → OPF `manifest/spine` → TOC 优先 NCX，回退 `nav.xhtml` → `SwiftSoup` 清理 XHTML。章节标题转 Markdown 标题并写入 `ParsedDocument.outline`。

**扫描版 EPUB**：逐 spine 章节解析 XHTML，按文档顺序收集 `<img src>` 与 SVG `<image xlink:href>` 的图片引用。若该章有效文字少于 80 且存在图片，则视为扫描页：

1. 图片从归档中按批取出（批内串行解码，避免并发读 ZIP 句柄），`ImageIO` 解码为 `CGImage`；
2. 每张图片先经 `OCRImagePreprocessor` 统一归一化（长边 ≤1500、灰度、1%/99% 对比度、3×3 锐化、可选 Otsu）；
3. 按 `rag_epub_ocr_engine` 选择后端：
   - `vision`：每文件最多 8 页并发，且全局 Vision OCR 并发由 `AsyncSemaphore` 限制在 CPU 核心数（4...12）；
   - `ovis`：串行调用 OvisOCR2，输出经 Markdown/HTML 表格清理；
4. 每张图片对应一个 `<!-- page N -->` 页标记，按 spine 与图片顺序拼接；单页失败跳过、不影响整本；
5. 章节标题由 TOC/原 XHTML 标题补回，随后走与 PDF 相同的 `DocumentCleaner`。

`rag_epub_ocr_engine` 默认 `vision`（无需额外模型）；选择 `ovis` 但视觉模型不可用时，仅在确实遇到扫描页时报明确错误。`rag_ocr_preprocess` / `rag_ocr_binarize` 同时作用于 PDF Vision 与扫描版 EPUB 两条路径。

### 5.7 切片

1. **结构**：按 Markdown `#`、`第X章/节`、数字编号、中文序号识别标题，维护标题栈生成 heading path；
2. **语义**：`NLTokenizer` 切句 → 内置 `potion-multilingual-128M`（int4 ONNX，纯 CPU，静态词向量，无 512 token 位置上限）按 32 句一批计算相邻句余弦 → 低分位阈值断开；模型不可用时退化为词 Jaccard；
3. **递归**：段落 → 换行 → 句号 → 空格 → token 窗口，严格限制 token 预算；
4. **overlap**：从上一块尾部按 token 预算取尾，并向后挪到自然句界；overlap 计入 `chunk_size` 总预算。

默认 `chunk_size=800 token`、`overlap=80 token`（10%，含在 800 内）。同步时优先用模型自带 `tokenizer.json` 做精确计数（不含特殊 token），分词器不可用时退回标定过的保守估算器（`EmbeddingTokenEstimator`）：纯中文约 1 字 ≈ 1 token、英文约 3.5 字符/token。默认 jina-embeddings-v3 声明窗口为 8192 token，但 embedding 推理前统一压到 1024 token，默认 800 token 的切片完整计算、不会被截断；若切片大小超过推理输入上限（1024 token，或改用 bge 等更小的 512 窗口模型），同步时自动压到该上限，overlap 同步压到上限的 10%。旧配置的默认 500/50（bge 512 窗口）会自动迁移到 800/80，自定义值保持不变。所有切分路径（语义断开、递归分隔符、token 窗口）都保证在句子结束处断开。

**切片参数只有一处来源**（设置面板的 `rag_chunk_size` / `rag_chunk_overlap` / `rag_semantic_chunking`），不允许任何环节再按与它无关的固定小值处理：

- 切片环节：`RAGEngine.resolvedChunkingOptions(config:embedding:)` 是唯一收口入口，`TextChunker` / `SemanticChunker` / `RecursiveChunker` 全部只用这份 `ChunkingOptions`；收口上限来自 provider 的 `EmbeddingTokenCounting.maxContentTokens`（MLX / ONNX 取 `config.json` 的 max sequence length 与 1024 token 推理上限的较小值、ONNX 额外扣 document 前缀、GGUF 的 2048 窗口同样压到 1024），同步开头打印一次「切片参数 N token（含 overlap M）」，被收口时附注面板设置值；
- 入库与增量：切片大小 / overlap / 语义切片开关 / embedding 后端与目录都进 ingest 签名，改任一项都会逐文件重建，不会因「文件本身没变」而继续沿用旧切片；
- 检索呈现：`searchFormatted` 单条上限取 `max(配置值, 切片 token × 1.5 + 64)`，总量上限取 `max(配置值, 条数 × 单条上限)`（封顶 L0 硬上限 20k 字符）。切片调大后不会继续按固定的 1500 字符截短「切了长块却只看到前半段」；
- Agent 侧：`AgentConfig.mainLLMOnlyKeys` / `auxLLMOnlyKeys` 白名单之外任何配置差异（切片、知识库目录、embedding / reranker 后端、OCR……）都会让「加载主 / 辅助模型」走完整 `applyConfig` 重建 Agent 与 `RAGEngine`，而不是只替换 LLM 槽位（`RAGEngine.config` 是 init 快照）；
- 面板反馈：切片 Stepper 在超过当前 embedding 推理输入上限（1024 token 与模型窗口取小）时显示「实际生效：N token」，`LocalModelFactory.embeddingContentTokenLimit(config:)` 与 ingest 用同一个 provider 实例换算，两处口径不会漂移。

### 5.8 独立 Markdown 转换（转换工具）

设置窗口「PDF OCR 设置」行末的「转换工具」按钮打开独立 `Window`（`markdown-converter`），把单个文件或整个目录批量转换为 Markdown。转换与知识同步共用同一套解析链路，但**不切片、不 embedding、不写 manifest / 向量库**：

- `MarkdownConversionService`（actor）：校验源路径与输出目录 → 扫描文件 → 逐文件 `DocumentParserRegistry.freshParser(for:options:)` 解析 → `DocumentCleaner` 兜底 → 原子写入 `.md`；
- 可转换格式直接取自 `RAGEngine.supportedExtensions`，与同步完全一致；Office 同时包含现代 OOXML 的 `.docx` / `.xlsx` / `.pptx` 与旧版二进制的 `.doc` / `.xls` / `.ppt`；
- 单文件输出为 `<输出目录>/<文件名>.md`；目录递归时保留相对子目录结构，输出目录位于输入目录内会自动 `skipDescendants`，避免把上次结果再次转换；
- 同批同名（`a.txt` 与 `a.html`）通过 `usedOutputs` 依次生成 `a.md`、`a-2.md`；单个文件失败写入 `error` 后继续后续文件，不中断整批；
- `MarkdownConversionProgress` 携带阶段（scanning / parsing / writing / finished）、当前文件序号与总数、页序号与总数、成功/失败数、总体进度；解析占单文件进度 90%，清洗与写盘补足剩余部分；取消在文件边界与解析回调中协作式检查（含 `AgentError.cancelled`）；
- UI 侧 `MarkdownConverterState` 只负责选择路径、启动/取消任务和展示进度；关闭窗口时 `cancel()` 正在进行的转换，避免后台继续占用 OCR/GPU。

配置来源是打开窗口瞬间的快照 `AppViewModel.converterConfig`（`nil` 时回退 `model.config`），包含面板上尚未保存的 PDF / EPUB OCR 引擎、自定义 OCR 模型路径、mmproj、归一化与二值化开关；若选择 `.custom` 但没有模型路径，快照会自动回退 `.vision`。该快照只用于本次解析，**不写回 `config.json`，也不重建 Agent**。

### 5.9 HTML / XHTML

`SwiftSoup` 解析 → `HTMLMarkdown` 转 Markdown（标题、段落、列表、表格、引用、代码块，纯 `<b>` 段落识别为弱标题并进入大纲）。网页模式去掉 `script/style/noscript/nav/footer`；`<header>` 只在内部没有 `h1/h2/h3` 时删除，避免连文章主标题一起丢掉。按节点顺序遍历，`<body>`/`<div>` 下的裸文本（没有 `<p>` 包裹）也会保留；`<li>` 内部的块级子元素按单行拼接，不会把 Markdown 列表拆断。转换后用 `.structured` 档清洗。

- **编码嗅探**：`DocumentTextDecoder.decodeHTML` 先看 BOM，再用严格 UTF-8 试解码；失败时读前 8KB 的 `<meta charset>` / `<?xml encoding>` 声明（big5 / shift_jis / euc-jp / euc-kr / gb2312 等，另有 GB18030 兜底），最后才退回有损 UTF-8；
- **本地框架接力**：浏览器「网页另存为」会把正文单独存成 `<页面>_files/N.html`，只读主文件会得到空正文。正文短于 400 字符且深度 < 2 时，收集 `iframe/frame/object` 的 `src`/`data`，只接受文档类扩展名的本地相对路径（拒绝 `http(s)`/`data:`/`javascript:`/`blob:` 等，用已访问集合防环，最多 8 个候选），取正文最长且长于当前结果的一份，来源写入 `metadata["embedded_source"]`；
- **空正文诊断**：确实取不到正文时抛出可读原因（正文在框架里但找不到本地文件 / 页面依赖 JavaScript 渲染（含 N 个脚本）/ 无可提取文本 / 全部是导航噪声），不再静默产出 0 字符的「成功」结果。
- 依赖 JavaScript 渲染的页面（前端应用外壳、需要登录的在线文档导出页）不做无头渲染：转换工具与知识同步是批量离线路径，不会为单个 HTML 拉起 WebKit。

### 5.10 现代 Office（DOCX / XLSX / PPTX）

`ZIPFoundation` + `AEXML` 直接读 OOXML，不依赖外部转换器；XML 用 `shouldTrimWhitespace=false` 解析，再按 `xml:space="preserve"` 决定是否 trim，避免「第 1 章」这类前后带空格的文本被吃掉空格。

- **DOCX**：按 `w:body` 顺序输出段落与表格。`w:br`/`w:cr` 转换行、`w:tab` 转制表符；跳过批注、修订删除文本、域代码与注音（`rPh`/`rt`）。标题级别依次取 `pPr/outlineLvl`、`pStyle` 的 `Heading N` / `标题 N`，最后回退 `word/styles.xml` 的样式名与 `outlineLvl`（含 `basedOn` 继承）——WPS 导出的样式 ID 常只是 `1`/`2`，不查样式表会漏掉整篇标题。列表按 `numPr` 与 `numbering.xml` 的 `numFmt` 输出 `- ` / `N. `，按 (numId, level) 计数并在回到上层时重置深层计数；表格按 `gridSpan` 补列；脚注/尾注按 `footnoteReference`/`endnoteReference` 的出现顺序编号为 `[^n]`，末尾追加「## 脚注 / ## 尾注」列表并写 `metadata["footnotes"]` / `["endnotes"]`。
- **XLSX**：`sharedStrings`（跳过注音 `rPh`）+ `styles.xml`（`cellXfs` → `numFmtId`，含自定义 `formatCode`）。按 `t` 类型处理 `s`/`inlineStr`/`str`/`b`/`e`/数值；日期序列号按 1900 / 1904 系统换算（含 1900 虚构闰日补偿），百分比样式输出 `50%`；单元格文本先转义换行与 `|` 再进 GFM 表格，避免多行单元格把表格拆断；单表上限 20000 行 / 256 列，命中上限时写 `metadata["truncated_sheets"]`，不做静默截断。
- **PPTX**：按 `presentation.xml` + 关系取幻灯片顺序，文本框逐段落输出（`a:br` 转换行、跳过幻灯片编号域），表格转 Markdown，SmartArt 从 `ppt/diagrams/dataN.xml` 取数据点文本；演讲者备注经 `notesSlide` 关系读取，跳过节标题/页码/日期占位符，以 `**演讲者备注**` 追加到该页并写 `metadata["notes_slides"]`；小节标题为 `## Slide N：<标题>`。

### 5.11 旧版 Office（DOC / XLS / PPT）

`LegacyOfficeParser` 按扩展名分派到三个内置提取器，直接读取 OLE2 复合文档，不依赖 LibreOffice、Python、`textutil` 子进程，也不新增运行时依赖。`OLE2CompoundFile` 统一处理 512/4096 字节扇区、DIFAT/FAT/miniFAT、目录项与大小写不敏感流名，并检测链循环、越界与截断。

- **DOC（Word 97–2003）**：AppKit `NSAttributedString` 读取正文/表格/字体属性；以字符数加权众数字号作为正文字号，按字号启发式生成 `#`/`##`/`###` 标题，列表用 `NSParagraphStyle.textLists` 或 `•`/`1.` 等前缀识别；再导出 HTML 并经 `HTMLMarkdown` 转 Markdown。metadata 写 `engine=doc`、`legacy_format=word-97`、`heading_detection=font-size`。RTF/HTML 伪 `.doc` 仍由系统导入器识别。
- **XLS（Excel 97–2003 / BIFF8）**：读取 `Workbook` 流，解析 `BOUNDSHEET`、`SST`+`CONTINUE`、`FORMAT`/`XF`、`DATEMODE`、`FILEPASS`，逐 sheet 处理 `LABELSST`/`LABEL`/`NUMBER`/`RK`/`MULRK`/`FORMULA`/`BOOLERR`/`BLANK` 等记录；日期按 1900/1904 系统转 `yyyy-MM-dd`，百分比输出 `12%`，常用公式做有界 token 反编译并保留缓存值。每 sheet 输出 `## Sheet: 名称` + GFM 表格，metadata 写 `engine=xls`、`legacy_format=biff8`、`sheets`、`formula_unparsed` 与行列截断标记。只有 `Book` 流（BIFF5）返回不支持。
- **PPT（PowerPoint 97–2003）**：读取 `PowerPoint Document` 流，按记录头 `recVerInstance` / `recType` / `recLen` 有界遍历（容器 `recVer=0xF`，深度上限 64、总数上限 100 万）。幻灯片顺序优先取 `SlideListWithText` + `SlidePersistAtom`，缺失时回退 `Slide` 容器顺序；`TextHeaderAtom` 区分标题/正文/备注，`TextCharsAtom` 按 UTF-16LE、`TextBytesAtom` 按 Windows-1252（非法回退 UTF-8）解码；备注按 `NotesAtom.slideIdRef` 挂到对应页。输出 `## Slide N：标题`、正文段落与 `**演讲者备注**`，metadata 写 `engine=ppt`、`legacy_format=ppt-97`、`slides`、`notes_slides`、`text_atoms`。PPT95 与加密文件返回不支持。

三种格式统一通过 `finish(profile: .structured)` 清洗，并接入 `RAGEngine.supportedExtensions`、`DocumentParserRegistry` 与 `DocumentCleaner.defaultProfile`。共享上限包括 512MB 文件、256MB 单流、2000 万字符正文、`.xls` 每 sheet 20,000 行 / 256 列 / 100 sheet、`.ppt` 10,000 页与每单元格 4096 公式 token；命中上限时写 `truncated` 等 metadata，不做静默截断。扩展名与实际格式不符、OLE2 损坏、加密、BIFF5、PPT95、空正文均返回带文件名的 `parse` / `unsupported` 错误。

## 6. 本地模型层

### 6.1 模型注册

`LocalModelRegistry` 按模型种类解析目录：

1. 配置显式路径（`/`、`~`、`./`、`../` 开头；不存在时直接报错）；
2. 相对路径按当前工作目录解析（存在时）；
3. `<workspace>/models/<name>`；
4. `~/base-agent/models/<name>`；
5. HuggingFace / FastEmbed 缓存（含 `models--org--name/snapshots/<rev>` 布局）。

旧配置常见的 `models/<name>` 写法会同时尝试去掉 `models/` 前缀后再拼接模型根目录，避免解析成 `<workspace>/models/models/<name>`。主/辅模型未配置时使用默认名 `qwen3.5-4b-agentic-coder-v4-4bit-mlx` 与 `Qwen3.5-2B-MLX-4bit`。

ONNX 文件查找顺序：`model.onnx`、`model_quantized.onnx`、`onnx/model.onnx`、`model_int8.onnx`。

### 6.2 ONNX

`ONNXRuntime.swift` 封装 `OnnxRuntimeBindings`：

- `OrtEnv` 进程级单例；
- `OrtSession` 持有输入/输出名，线程安全运行；
- `OrtValue` 持有输入 `NSMutableData`，防止运行时读取已释放内存。

Embedding（nomic）：`search_document:` / `search_query:` 前缀、mean pooling、L2 归一化。Reranker（bge-reranker）：query/document 成对输入，logits → sigmoid。

FastEmbed 类型复用 ONNX 运行时，目录解析包含 `~/.cache/fastembed`。

### 6.3 MLX

- `MLXLLMService` 使用 `MLXLLM` / `MLXLMCommon` 加载 Qwen3 系模型，流式输出 content 与 reasoning；支持 tools；`maxTokens` 按「contextWindow - prompt/schema 估算 - 64」动态收紧；框架未解析出工具调用时从 `<tool_call>`/JSON 围栏兜底解析，且只接受本次请求声明过的工具名，避免普通 JSON 误触发工具。
- **跨轮 KV cache 复用**：服务自己持有 raw `[KVCache]`、`LMOutput.State`、`cachedTokenCount` 与 `sessionTranscript`，不走 `ChatSession` 的自动裁剪（Qwen3.5 的 Mamba/GDN 层 `isTrimmable == false`，裁剪会退回全量 prefill）。首轮用完整 `messages + tools` prepare；成功后缓存预填充/解码后的 state 与 token 数。后续轮次比较外部消息与轨迹的公共前缀，只把新增的 user/tool 消息用 `container.prepare` 渲染为 delta 追加到原 cache；外部重复出现的已生成 assistant 消息会跳过（`pendingGeneratedAssistant`）。增量中的 tool 结果会先改写成 `<tool_response>` 包裹的 user 消息（连续多个合成一条），因为 chat template 只渲染增量时看不到前一条消息，原生 `tool` 分支会漏掉 `<|im_start|>user` 头；改写后与完整 prompt 的尾部逐 token 对齐（`KVDeltaTemplateTests` 覆盖单条/连续 tool 结果）。当公共前缀断裂、无新增消息、缓存 token + delta 超过 `contextWindow - 512` 或 prepare 失败时，回退为一次完整重建并换新 cache。
- **重建前缀复用**：预热成功后额外保留一份未推进的 `warmupCacheSnapshot`（`KVCache.copy()`）与 `LMOutput.State`、前缀 token ID。历史折叠/滑窗/rollback 触发重建时，先比较新完整 prompt 的前缀 token 是否仍等于预热前后缀；命中则从快照复制 cache，只 prefill 动态历史部分，避免重新计算 4~5k token。实测 5471-token 重建耗时从约 34s 降到 5.3s（只 prefill 805 token），626-token 重建约 4.1s。`close()` 释放快照；工具清单变化时快照不参与匹配。
- **加载后预热**：`MLXLLMService` 实现 `WarmupLLMService`。`preload()` 成功后，AppModel 先 `await Agent.connectMCP()`（工具清单会进入 system 前缀），再用 `DefaultMessageGenerator` + `MLXTokenizerBridge.applyChatTemplate(addGenerationPrompt: false)` 渲染「工具定义 + `BASE_SYSTEM_PROMPT`」的纯前缀（当前 4736 tokens），通过一次 `TokenIterator` 初始化完成 prefill，保存 `[KVCache]`、`LMOutput.State`、`cachedTokenCount` 和 `sessionTranscript=[system]`，不生成 token。首次正式请求直接命中该前缀（实测 `reuse=true cached=4736 delta=216`）。预热使用与正式请求相同的 `enable_thinking` 和缓存计划；tools 指纹变化时 `chatStream` 强制重建，避免 system 前缀不一致。
- **prefill 批量**：`AgentConfig.promptBatchSize` / `auxPromptBatchSize`（JSON 键 `prompt_batch_size` / `aux_prompt_batch_size`，默认 512）传入 `MLXLLMService`，非 0 时设置 `PrefillParameters.stepSize = max(64, value)`；正式请求与预热使用同一参数。配置窗口主/辅模型的 `batch` 字段与该键对应，`0` 表示沿用 MLX 默认值。该参数只影响长 prompt prefill 的分块宽度，不改变生成内容。
- **KV 开关（主/辅各自独立）**：配置窗口主模型与辅助模型的参数行末尾依次是「思考」「KV复用」「KV量化」，仅在消费它们的后端（MLX-LM / GGUF）出现；ONNX 自动复用 `past_key_values`、MLX-VLM 每轮重建 prompt，故不显示。`llm_kv_reuse` / `aux_llm_kv_reuse` 控制跨轮前缀复用（关闭即每轮全量重建），`kv_cache_int8` / `aux_kv_cache_int8` 控制 KV int8 量化（MLX 的 `kvBits=8` QuantizedKVCache、GGUF 的 q8_0 KV）。这四个键都在对应的模型实例缓存键里，改完点「加载模型 / 重新加载」即用新值重建实例；辅助模型的两个键同时落在 `AgentConfig.auxLLMOnlyKeys` 白名单内，因此重载辅助模型不必重建 Agent，但换主模型也不会吞掉它们的变化。
- **投机解码限制**：mlx-swift-lm 的 `SpeculativeTokenIterator` 在初始化时强制 `canTrimPromptCache(mainCache)` 与 `draftCache` 均为真，以便拒绝草稿后回退 token。当前主/辅模型都是 Qwen3.5 hybrid，`Qwen35.newCache` 为 GDN 层返回 `MambaCache`（`isTrimmable == false`），初始化会抛 `Speculative decoding requires trimmable KV caches`；`MTPSpeculativeTokenIterator` 虽支持混合缓存的单 token 回退，但两个模型的实际 safetensors 中没有 `mtp` 权重（config 的 `mtp_num_hidden_layers=1` 未落盘），也无法使用。因此当前模型组合下没有可用的投机解码路径，服务保持常规逐 token 生成。
- **内存上限**：`AgentConfig.mlxMemoryLimitMB`（默认 0 = min(物理内存 65%, 9.6GB)）通过 `MLX.Memory.memoryLimit` 设置权重+KV+buffer 的总闸门；`mlxCacheLimitMB`（默认 512，运行时夹在 256...2048）限制 MLX 空闲 buffer，只影响可复用 buffer，不含模型权重与 KV；实测 jina-v3 embedding 的复用 buffer 工作集约 1.27GB，1GB 与 2GB 的吞吐基本一致，2GB 仅多留空闲缓存；`kvCacheMaxTokens`（默认 32768，可在配置窗口「KV 上限」调整，0 表示跟随 Context）与 `auxKvCacheMaxTokens`（默认 16384）是主/辅模型 KV 的硬上限，`effectiveMainContextTokens` / `effectiveAuxContextTokens` 取 `min(配置上下文, KV 上限)`。`LocalModelFactory` 用有效上下文构造 `MLXLLMService`，`Agent` 创建 `Session` 时把内核预算也 clamp 到主模型有效上下文；`MLXLLMService` 在完整 prompt 超过预算时直接抛错，避免 KV 无界增长。预热前缀快照只在 ≤8192 token 时复制，避免常驻内存翻倍。辅助模型的 KV 行为独立可配：`aux_llm_kv_reuse`（默认 `false`，配置窗口辅助模型的「KV复用」）关闭时每次后台摘要/事实抽取结束后调用 `invalidateKVCache()`，不保留跨任务 KV；开启后保留前缀缓存供相同前缀跨调用复用。`kv_cache_int8` 与 `aux_kv_cache_int8`（各默认 `true`）分别控制主/辅模型的 KV int8 量化。RAG 检索 `topK` 封顶 20，限制 reranker 候选批量。
- **模型常驻策略**：主模型在启动预加载开启或手动加载后权重常驻，Reranker 持续使用；辅助模型仅在 `auxEnabled`（`aux_enabled`）为真时常驻，关闭时 Agent 的 `auxLLM` 保持 `nil`，RAG 精简跳过，后台记忆/总结回退主模型；Embedding / OCR 只在检索/解析时使用，`AppModel` 在无前台活动 3 分钟后调用 `LocalModelFactory.unloadIdleRAGModelWeights()` 释放其权重，provider 保留并在下次调用时按需重载。
- 为保持前缀稳定：`Agent.systemPrompt()` 只输出稳定的 `BASE_SYSTEM_PROMPT`；工作记忆、当天事实、checkpoint、命中技能与知识库状态由 `dynamicContextPrompt()` 生成并拼在 user 文本尾部（同一次用户请求内缓存）。历史折叠/回滚、`reset()`（清空对话）、`switchLLM()`、模型卸载、生成失败或取消都会调用 `invalidateKVCache()` 丢弃缓存，避免带着被折叠掉的工具步或已清空的历史继续生成。
- 服务每次调用输出 `[mlx-kv] reuse=… cached=… delta=… prefill_ms=… common=… transcript=…`，重建时额外输出 `reason=`；框架 info 输出 `[mlx] prompt=… cached=… generated=… tps=…`；`usage` 同时返回 `prompt_tokens`（含缓存）与 `cached_prompt_tokens`。取消时 `onTermination` 直接取消底层 `generateTask`，避免等待下一个 token 才退出。
- `MLXLLMService` 实现 `PreloadableLLMService` 与 `ClosableLLMService`：`preload()` 加载容器并做一次 chat template 探测；`close()` 卸载容器与 tokenizer、释放前缀快照（不在关闭路径同步 clearCache）。主/辅模型都支持在配置窗口手动加载/卸载；启动时按 `auto_preload_main`（默认 `true`）决定是否预加载主模型，辅助模型仅在 `aux_enabled=true` 时预加载。参数（context/temp/top_p/min_p/top_k/repeat/batch/thinking/KV 复用与量化）参与模型实例缓存键。
- `MLXEmbeddingProvider` 使用 `MLXEmbedders` 加载本地 MLX embedding 目录，tokenizer 编码/截断/按 eos padding，`context.model(...)` 输出后做 pooling + L2 归一化；nomic 模型自动加 `search_document:` / `search_query:` 前缀，隐藏维度从 `config.json` 读取。
- `MLXReranker` 使用 `MLXEmbedders` 的 encoder reranker（`allowUnverifiedModel: true`），按 `RerankScoreKind`（normalizedRelevance / cosineSimilarity / logit）把分数归一到 0...1，并按原始文档下标回填。
- `OvisVLMService` 使用 `MLXVLM` 加载 OvisOCR2。OvisOCR2 的 config 为
  `model_type=qwen3_5` / `Qwen3_5ForConditionalGeneration`，直接复用 mlx-swift-lm
  已注册的 Qwen3.5 VLM 实现；仅对真正未注册的 Ovis2 架构抛错，不伪造 OCR 结果。
- `ONNXReranker` 兼容 logits 与概率两种导出：全部落在 [0,1] 时保留概率，否则 sigmoid。
- MLX 空闲 buffer cache 上限默认 512MB、运行时夹在 256MB...2GB，并设置全局内存硬上限（默认 min(物理内存 65%, 9.6GB)）；配置切换时清空模型缓存。
- 本地模型按「类型 + 路径 + 参数」缓存单例，加载过程由 actor 串行保护；`LocalModelFactory.unloadLLMCaches()` 只清 LLM 缓存与 MLX buffer。

### 6.3.1 GGUF 与 ONNX（进程内）

- **GGUF（llama.cpp C API）**：通过官方 `llama-b11815-xcframework.zip` 以 `binaryTarget` 引入，`LlamaCppBackend` 进程内调用 `llama_backend_init`，不启动 `llama-server`，也不依赖外部二进制或 Python。
  - 模型与上下文：`LlamaCppModel` 用 `llama_model_load_from_file` 加载权重，`n_gpu_layers` 来自 `llama_gpu_layers`（默认 99，Metal 不可用时回退 0）；`LlamaCppContext.make` 设置 `n_ctx` / `n_batch` / `n_ubatch` / `swa_full`。
  - LLM：`LlamaCppLLMService` 用 GGUF 元数据里的 Jinja 模板渲染消息（`swift-jinja`，支持 tools 与 `enable_thinking`）；采样走 llama.cpp sampler chain（top-k / top-p / min-p / temperature / repetition）；流式 token 经 UTF-8 拼帧、`ThinkSplitter` / `ToolTagSplitter` 后输出；工具调用同时兼容 `<tool_call>{...}</tool_call>` 与 Qwen `<function=...><parameter=...>` 格式。
  - KV 复用：保存已解码 token 序列，下一轮计算公共前缀；混合 SSM 模型（Qwen3.5）不支持 `llama_memory_seq_rm` 部分裁剪，因此仅当前缀完全一致时续写，否则 `llama_memory_clear` 整段重建。预热只缓存到 system + tools + user 头，正式请求可精确续写（实测 `cached=328/341`）。
  - VLM：`LlamaCppVLMService` 用 `mtmd_init_from_file` 加载 mmproj，页面图片转 JPEG 后由 `mtmd_tokenize` 替换媒体占位符，`mtmd_helper_eval_chunks` 编码图像并继续文本解码；mmproj 可由 `rag_ocr_mmproj_path` 指定，留空自动查找模型同目录 `mmproj*.gguf`。实测 Qwythos-9B 正确识别图片文字。
  - Embedding：`LlamaCppEmbeddingProvider` 以 `embeddings=true` 创建上下文，按模型 pooling（mean/CLS/last）取向量并做 L2 归一化；nomic 仍加 document/query 前缀。实测 768 维。
  - Reranker：`LlamaCppReranker` 要求模型使用 `LLAMA_POOLING_TYPE_RANK`，按 llama.cpp server 的 query/document 拼接方式构造输入并取分类头分数。
- **ONNX（onnxruntime-swift）**：`ONNXLLMService` 直接用 `ORTSession` 运行 decoder 图，不依赖 `onnxruntime-genai` 或 Python。
  - 图适配：要求 `input_ids` 与 `logits` 输出；动态识别 `attention_mask` / `position_ids` / `token_type_ids`；`past_key_values.*` 与 `present.*` 按名称后缀配对，空 KV 形状由 `config.json` 的层数、KV 头数与 head_dim 推导。
  - 生成：按 `chunkSize=512` 分块 prefill，逐 token 增量解码；采样支持 temperature / top-k / top-p / min-p / repetition；chat template 由 swift-transformers 渲染，工具调用复用统一文本解析。
  - KV 复用：仅在 prompt 精确扩展缓存前缀时复用 `past_key_values`；否则从空 KV 重建。
  - ONNX VLM：视觉编码器与图像 token 布局因架构而异，当前没有通用实现，`LocalModelFactory` 会明确报错并建议改用 MLX / GGUF，不会回退到 Python。
  - 空 KV 按 float32 + `config.json` 的层数/KV 头数/head_dim 初始化；fp16 past 或非标准 KV 布局的导出会明确报错，需针对性适配。
  - 当前机器没有 ONNX LLM 模型，生成路径未做推理实测。

### 6.4 Tokenizer

`TokenizerSupport` 使用 swift-transformers 的 `Tokenizers` 模块加载 `tokenizer.json` / `tokenizer_config.json`，负责 encode、截断、padding，供 ONNX embedding/reranker 使用。

### 6.5 远端 LLM 客户端

`OpenAILLMClient` 按 SSE 事件边界聚合：空行才提交事件，支持一个事件包含多行 `data:`、`:` 注释/心跳行与 `[DONE]`；tool_call 仍按 index 聚合，缺省 index 时按 id/name 判定新槽。内核在消费侧加 200ms 取消看门狗：用户取消时结束消费流，`onTermination` 取消 producer，进而取消底层 URLSession 任务。

请求级 `LLMRequestOptions(enableThinking: false, isolated: true)` 已贯通 API 后端：摘要等批量任务对兼容端点（DashScope / vLLM / llama.cpp 等）同时发送顶层 `enable_thinking` 与 `chat_template_kwargs.enable_thinking`，覆盖两类模板开关；官方 OpenAI / Azure 会拒绝未声明字段，客户端按 host 自动跳过。未显式覆盖时主对话请求不携带这些字段，`isolated` 对无共享会话的 HTTP 客户端无额外语义。

## 7. 记忆、技能、MCP

- **工作记忆**：`<workspace>/.agent/work_memory.json`，扁平 key-value，原子写。
- **长期记忆**：`<workspace>/.agent/long_memory.json`（事实列表，支持语义检索与容量淘汰）。
- **知识图谱**：`<workspace>/.agent/long_memory.graph.json`，实体 + 观察 + 关系；embedding 不可用时用关键词回退。观察向量按文本去重后分批嵌入；裁剪只在真正超过实体/观察/关系上限时执行；共享实例在 Agent 关闭时落盘并从注册表释放。
- **技能**：`<workspace>/.agent/skills/<slug>/SKILL.md` + `skill.json`，frontmatter 解析 name/description/tags；`SkillIndex` 扫描 `skill.json`（入口缺失时回退 `SKILL.md`/`prompt.md`），`SkillRetriever` 语义/混合召回并按技能指纹缓存 BM25 索引。请求计数达到阈值后建议固化，但寒暄/简单问询不进入计数（`SkillManager.isTrivialRequest`），且只有本轮真正创建/更新过计划（`Session.planRevision` 变化）或显式触发长期蒸馏时才提示；`anchorPrompt` 里的技能固化 TIPS 也只在存在计划时注入。仅当主目录是 `<workspace>/skills` 时才镜像到 `.agent/skills`，镜像会覆盖更新。
- **MCP**：stdio JSON-RPC 客户端，支持 `initialize`、`tools/list`、`tools/call`，工具包装为 `AgentTool`，冲突时自动加 `mcp_<server>_` 前缀；服务端推送工具清单变化时动态替换注册表条目，刷新失败不影响旧工具。

## 8. UI 架构

`AppViewModel`（`@MainActor`）持有 Agent 与展示状态；`UICallbacks` 实现 `AgentCallbacks`，把后台事件 `DispatchQueue.main.async` 回主线程：

- `onContent` / `onReasoning` 先写入 50ms 合并缓冲，避免逐 token 触发整表重绘；`onContent` 先经过 `SummaryStreamFilter`，把协议标签 `<summary>…</summary>` 的内容转入思考缓冲，正文才进入对话区；流结束与兜底答案再用 `stripSummaryTags` 兜底；
- `onToolStart/End` → 工具事件列表（按工具名队列匹配并行调用）；
- `onPlanUpdated` → 计划面板；`onUsage/onTokenSpeed` → 顶部 token 统计；
- `confirm` / `ask_user` → 主线程 `NSAlert` 同步返回，确认默认拒绝。

**主窗口**采用单层 `HSplitView`：

- 左侧约 3/4：对话区从窗口顶部到底部；底部依次为居中 tokens、输入框与发送/停止按钮；
- 右侧：`VSplitView` 上半任务计划（目标、步骤状态、进行中徽标），下半思考过程，最下方状态栏（模型、同步进度、RAG 统计）；
- 右上角工具栏「配置」「日志」通过 `openWindow(id:)` 打开独立 `Window`，主窗口不再内嵌设置/日志区域。

**配置窗口**分为两个 `GroupBox`：

- Agent 模型配置：主模型支持本地 / OpenAI 兼容二选一；本地模式标题后带「启动时预加载」复选框（`auto_preload_main`，默认开启），两行（类型 + 路径 + 选择；参数 + 加载/卸载），API 两行（Base URL / API Key / 模型下拉 / 获取模型；参数 + 应用配置）。辅助模型固定本地布局，标题后带「启用」复选框（`aux_enabled`，默认关闭；未启用时「加载模型 / 重新加载」禁用）。Agent 区底部另有「运行参数」行：「最大迭代」（`max_iterations`，默认 15，1...50），行末「应用配置」保存。「启动时预加载」关闭后启动不加载主模型权重，但手动「加载模型」、`applyConfig` 恢复和同步结束后的恢复不受影响。
  - 「加载模型」走 `reloadMainModel` / `reloadAuxModel`：只关闭并替换目标槽位的模型实例，`preload()` 成功后 `switchLLM()` / 赋值 `auxLLM`，另一个模型保持常驻，不会被连带卸载。`reloadAuxModel` 在 `auxEnabled=false` 时只卸载旧辅助模型并跳过加载。
  - API 模式的「应用配置」和知识同步走 `applyConfig()`：停止在途对话、关闭旧 Agent、取消旧同步、清理缓存、按新配置重建 Agent，并按应用前的加载状态恢复主/辅模型；新配置关闭辅助模型时，即使旧辅助模型已加载也不恢复。
- 知识同步配置：工作目录 / 知识库；Embedding 行 = 类型 + 本地路径 + 选择… + **语义切片开关 / 切片大小 / overlap**（在「应用配置 / 同步知识」之前）；Reranker 行 = 类型 + 本地路径 + 选择… + **启用重排序开关 / TopN / 阈值**（在「向量去重 / 停止同步」之前）；向量库与 ANN 索引合并行 = 向量元素类型 / Matryoshka 模式与截断维 / **ANN 检索开关 / 自动构建开关** / ANN 索引摘要（来自 `rag_status` 的 `ann_index`）+「构建 ANN 索引 / 停止构建 / 删除索引」（放不下时整组折行，行末为「重建向量库」）。Embedding / Reranker / 向量库与 ANN 三组都用 `ViewThatFits`：单行放不下时按两级回退换行（切片 / 重排控件仍留在模型那一行），窗口极窄时再整体换行，避免控件被裁剪。同步按钮走 `applyConfig { syncKnowledgeBase(force: false) }`，确保先应用新配置再启动同步。高级区保留 OCR 与子批参数，另有「RAG 参数设置」行（`rag_query_timeout_seconds`，默认 5s，0 = 关闭）和「同步参数设置」行（启动时自动同步、`rag_ingest_concurrency`、`rag_vision_concurrency`、`mlx_cache_limit_mb`、`mlx_memory_limit_mb`），并用单独一行展示 8 个自适应子批参数；向量库待重建的红色提示显示在该合并行下方。
- 「PDF OCR 设置」行末的「转换工具」打开独立转换窗口：顶部为待转换文件（单文件或目录）与保存目录，下方为当前文件、当前环节与总体进度，最下方为逐文件结果列表。窗口使用打开瞬间的配置快照 `converterConfig`，不写回配置、不重建 Agent；关闭窗口会取消仍在进行的转换。转换按文件体积分批并发（≥32MB 单独成批串行，其余按 `rag_ingest_concurrency` 最多 6 并行），PDF 解析按体积收紧页级 worker / 在途页并分批产图，内嵌大图按目标尺寸降采样、超过 200MP 回退有界栅格化；只处理到写出 Markdown，不走切片 / embedding / 入库。

配置应用后先停止在途对话、关闭旧 Agent、取消旧知识库同步、清理模型缓存，再重建 Agent；连续应用配置由 `configGeneration` 保证只有最后一次生效。

- `pendingToolIndices` 在发送新消息、清空对话、应用配置时一起清空，避免工具事件按旧下标串到新列表；
- RAG 状态查询放到后台（`Task.detached(priority: .utility)`），通过 `ragStatusRefreshing` 防重入，并在 agent 切换时重新取新实例状态；首轮提示词只读 `RAGEngine.cachedStatus()` 快照，不在模型调用前打开数据库；
- 知识库同步完成只重载实际执行同步的引擎，配置切换后不会把旧结果作用到新 Agent；所有路径都会复位 `isSyncing`。
- 卸载主模型时把 Agent 的 LLM 切换为 `UnloadedLLMService` 并清空 LLM 缓存；卸载辅助模型调用 `Agent.unloadAuxLLM()`。重新加载需在配置窗口点击「加载模型」。
- 底部状态栏按「模型加载中… → 模型加载成功 → 模型预热中… → 预热结束 → 就绪」更新，失败显示「模型加载失败」/「预热失败」；加载与预热期间显示进度指示并禁用发送。主模型在启动预加载（`auto_preload_main=true` 时）、配置窗口「加载模型」、`applyConfig` 恢复三种路径下都会执行预热，辅助模型只加载不预热，且仅在 `auxEnabled` 为真时才允许加载。
- 生成、加载、预热、同步、ANN 索引构建期间互相禁用相关按钮与发送（发送还会等待索引构建结束，因为构建期间知识检索会被只读超时跳过），避免在途请求使用已关闭的模型。`applyConfig`/`swapModel` 会等待旧 `runTask` 结束，再用 `clearStreamingState()` 丢弃未 flush 的缓冲与 `streamingID`；50ms flush 任务带 `runGeneration` 校验，旧轮次迟到的 flush 不会写进新气泡。
- **同步期间释放模型**：`syncKnowledgeBase` 记录同步前的主/辅加载状态，手动路径先 `Agent.switchLLM(UnloadedLLMService())` + `unloadAuxLLM()` + `unloadLLMCaches()`，把权重、KV cache 与 MLX 缓冲释放后再开始 ingest；`applyConfig { sync }` 路径由 `pendingSyncRestore` 记录状态且不再并行预加载。同步开始（`startIngest`）、卸载（`suspendModelsForSync`）与恢复（`resumeModelsAfterSync`）三处都会检查 `auxEnabled`：关闭时既不会卸载/创建辅助模型，也不会在日志里声称重新加载。同步成功、失败或取消后统一按原状态重新创建/预加载服务，主模型重新预热，辅助模型只加载。同步期间模型操作和发送均被禁用。
- 停止同步的响应性：`stopSync()` 立即设置 `isStoppingSync` 与「正在停止同步…」，禁用停止按钮，同时 `ragEngine.cancel()` + `syncTask.cancel()`。`RAGEngine.ingest` 在文件循环、embedding 批次和解析完成后都检查 `cancelRequested || Task.isCancelled`；取消时不写 ingest 签名，结束时输出「同步已停止」。`syncGeneration` 保证旧同步迟到的收尾不会覆盖新同步状态。
- 输入框用 `onKeyPress(.return)` 实现 Enter 发送；若当前 field editor（`NSTextView`）`hasMarkedText()` 为真，说明中文输入法正在组合候选词，此时返回 `.ignored` 交给 IME 确认候选，避免先清空输入框再被 IME 回填成残留拼音。
- 流式内容更新时 `ScrollView` 不再逐帧执行动画；日志窗口复用静态 `DateFormatter`，避免长日志列表反复创建格式化器。清空对话同时复位 tokens/速度与 KV cache。

启动时按 `rag_auto_ingest`（默认 `false`）决定是否增量同步，避免全量/增量同步与对话争抢 embedding 模型和磁盘 IO；工具栏提供手动增量/强制同步与停止同步。

## 9. 并发与状态

- MLX 卸载/切换只释放模型容器与 LLM 实例缓存，不在关闭路径同步调用 `MLX.Memory.clearCache()`：上一次生成的 `asyncEval` 可能仍在 GPU 线程执行，与 command encoder 释放并发会触发 SIGSEGV；buffer 由 cache 上限（默认 512MB，最高 2GB）和后续生成自然回收。
- `SQLiteDatabase` 使用递归锁 + `FULLMUTEX`；事务持锁覆盖整个闭包，保证事务内多语句不被其它线程插入；写入用 `INSERT ... RETURNING rowid` 一次拿到主键。事务嵌套深度只在 COMMIT/RELEASE 成功后递减，提交失败也保持非负，避免后续事务被误判为 savepoint。
- `VectorStore` 写入/删除/搜索共用同一把递归锁；两段式查询不会被写入事务插入。
- `RAGEngine` 用 `ingestLock` 串行同步、`searchLock` 保护整段读；`close()` 在同步中记录 `closePending` 并在收尾后关闭；延迟关闭会重新抢占 ingest 标志，若已有新同步则保留 pending，避免误取消新任务；`clear()` 与同步串行；实例销毁时兜底关闭 SQLite 连接。
- 多文件 OCR：每文件按 8 页一批渲染，Vision 识别通过全局 `AsyncSemaphore` 限制在 CPU 核心数（4...12）；信号量在等待许可时响应任务取消，取消后立即归还/退出，不会把停止后的剩余页误记为失败页。
- `RAGEngine.status()` 默认复用最近 10 分钟的快照（同步/去重/清空/重载会主动失效）：切片数读 `VectorStore` 维护并持久化在 `meta.chunks_count` 的计数器（写操作增量更新、事务失败回滚），来源数与来源名单读 manifest（只返回前 256 个），不再执行 `COUNT(*)` / `COUNT(DISTINCT source)` / `DISTINCT ... LIMIT`。56GB、2115 万切片的库实测三者分别约 181s / 186s / 13.7s，正是首轮对话“看起来卡住”的原因；旧库没有计数器时回退 `MAX(rowid)`（O(1)，允许略高于实际值）。UI 状态栏与 Agent 系统提示都使用总数。
- `Session` 可变但只在 Agent 线程使用；UI 只读快照（`onPlanUpdated` 传值）。
- 知识库只读查询（打开库 / 状态 / 检索）统一受 `rag_query_timeout_seconds`（默认 5s，0 = 关闭）约束：`SQLiteDatabase.withDeadline` 通过 `sqlite3_progress_handler` 在 VM 层中断超期语句（`SQLITE_INTERRUPT` → `AgentError.timeout`），`VectorStore.withQueryDeadline` 限时取切片锁，`RAGEngine.withStoreBounded` 限时取 `searchLock` 并限时等待后台 opener —— 打开库（含上次中断事务的 WAL 恢复）只在后台进行，同一时刻只有一个连接，超时即跳过本次查询并在 30s 内复用「跳过」快照。同步/去重/清空/重载仍是无超时的长任务（有进度与停止按钮）。
- 后台事实抽取/蒸馏使用独立 `Task.detached`，并用 `backgroundLock` 防堆叠；日常事实写入复用共享 `WorkMemory` 实例，避免旧快照覆盖。
- ANN 索引构建复用 ingest 标志：与同步/去重/清空串行，块间检查取消，写入不额外加锁（整段在 `withStore` 内）；构建期间只读查询按 `rag_query_timeout_seconds` 跳过（与同步期间一致），UI 由 `isBuildingANN` 与同步/去重/模型加载互相禁用。
- 知识图谱落盘 0.5s 防抖，`flush()`/`close()` 强制落盘；共享实例在 Agent 关闭时统一 flush 并释放。
- MCP 客户端 `start()` 串行化并等待握手完成；接收缓冲与结果渲染均有上限。
- 取消是协作式的：内核在流事件、工具执行前、轮次边界轮询 `AgentCallbacks.isCancelled`；UI 同时 cancel 运行 Task。LLM 流额外有 200ms 看门狗，静默流也能及时退出；Web 下载用 `withTaskCancellationHandler` 取消 dataTask。

- 索引指纹 = `embedding.identifier | dimension | matryoshkaDim | elementType`（未启用截断时记 0）。指纹不符时非空库只标记待重建，不静默删数据：向量检索关闭、`ingest` 拒绝写入、全文检索仍可用；设置面板与 `rag_status` 显示 `rebuild_reason`，用户执行「重建向量库」后才清空并按当前配置全量同步。空库直接采纳新配置；
- chunk overlap 不小于 chunk size 时重置为 chunk size 的 10%；
- 知识库只读查询超时 `rag_query_timeout_seconds` 默认 5s（0 = 关闭）；

- 损坏的 JSON 备份为 `.corrupt` 后以默认配置启动。

## 12. 扩展点与限制

- 新增文档格式：实现 `DocumentParser` 并注册到 `DocumentParserRegistry`。
- 新增 embedding/reranker：实现 `EmbeddingProvider` / `RerankProvider`，在 `LocalModelFactory` 接入。
- 主/辅 LLM 支持 MLX-LM / MLX-VLM / GGUF / ONNX；OCR VLM 支持 MLX / GGUF+mmproj；Embedding / Reranker 支持 ONNX / FastEmbed / MLX / GGUF。GGUF 与 ONNX 均在进程内运行，不需要外部 server 或 Python。缺少运行时或模型时会明确报错，不会静默降级。
- sqlite-vec KNN 的 `k` 上限为 4096；超大语料定向检索采用多轮放大与第二阶段过滤。
- ANN 索引是「块内 IVF + 按元素类型粗排」的近似方案：`rag_ann_nprobe` 越大越准也越慢（默认 1）；int8 / bin 粗排可能漏掉少量远离簇心的近似解，靠 `rag_ann_rescore` 条精确重打分与 `rag_ann_enabled=false` 的回退路径兜底。索引与向量表同文件存放，ANN 磁盘占用约为向量表的 25%（fp32）/ 1 倍（int8）/ 1.1 倍（bin）；尾块超过 128MB 读取预算时必须重建（`ann_needs_rebuild`），否则这些切片只能走精确路径。
- 向量元素类型：`fp16` 不被 sqlite-vec 0.1.9 支持，配置为 fp16 时打开向量库直接报错，必须改用 int8 / fp32 / bin。int8 使用对称量化，单位向量上误差较小，但排序结果仍可能与 fp32 略有差异；bin 只有 1 bit/维，相似度是汉明距离折算，召回精度最低，适合「体积优先」场景。精确扫描路径从库内按元素类型解码后重算，因此同样继承量化误差。
- Matryoshka 截断会丢失高维信息：默认 256 维在 jina-v3 上召回损失有限，nomic 或更低的 128 维召回会下降；截断后必须重新归一化，否则余弦相似度与 ANN 簇心都会失真。截断维与元素类型都进索引指纹，切换后需显式重建。
- 配置与索引指纹不符时不会自动清理旧数据：向量检索暂停、同步被拒绝，直到用户在设置面板执行「重建向量库」。这是有意为之，避免误改配置导致大规模知识库被静默删除。
- OvisOCR2 使用 `model_type=qwen3_5`，由 mlx-swift-lm 的 Qwen3.5 VLM 实现加载；真正未注册的 Ovis2 架构明确报错，不静默切换引擎。
- PDFKit 不暴露内嵌图片/表格坐标：Ovis 表格页用文本对齐启发式整页识别，未实现参考项目的表格裁剪回填。
- EPUB 按 spine 文件分章，未按 TOC 锚点二次切章。扫描版 EPUB 只在「章节文字层低于阈值且含图片」时对该章图片逐页 OCR；CSS 背景图、非 `<image>` 引用的 SVG 矢量图、加密字体渲染的文字不在识别范围内。
- 子进程未 `setsid`，用递归进程树终止；极端双重 fork 守护进程仍可能逃逸。
- 本地模型未下载时对应工具返回可诊断错误；不会退化为远端 API（除非配置为 `api`）。
